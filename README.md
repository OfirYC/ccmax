# CCMAX

CCMAX 是一个多平台账号聚合和多级代理结算工作台。当前适配：

- Gatelink（`cc.gatelink.dev`）：平台主账号 OAuth 上号、实时账号同步。
- AI008（`ai008.xyz`）：平台主账号 OAuth 上号、refresh token 导入、账号同步和历史用量查询。
- Mini CC Gateway（`207.57.170.28:8096`）：Cookie 会话登录、OAuth 上号、refresh token 导入、账号同步、启停和历史用量查询；新账号按上游规则固定使用默认策略、分组和 CC 模板。

代理只登录 CCMAX。Claude 账号提交到平台主账号，账号经真实授权邮箱校验或管理员核实后，在 CCMAX 中固定归属于对应用户；同一个 Claude 账号可以绑定多个平台。平台密码、refresh token 和 OAuth 会话只在服务器端加密处理，浏览器不会得到主账号密码。

**每个 Claude 账号必须绑定一条固定出口代理，同一账号上到所有平台时统一使用这条代理，一条代理只能被一个账号占用。** 支持 HTTP、HTTPS 和 SOCKS5H；SOCKS5 地址统一转成 SOCKS5H。未绑定、已禁止上号或已有平台代理尚未核对时，系统阻止新授权、RT 导入和启用操作。

## Railway 部署

1. 在 Railway 新建一个 Project，添加 **PostgreSQL** 服务。
2. 选择「Deploy from GitHub Repo」，选择 `abingyyds/ccmax`；Railway 会读取根目录 `Dockerfile` 构建。
3. 在 CCMAX 服务的 Variables 中设置以下变量（`DATABASE_URL` 使用 Railway 的变量引用）：

   ```text
   DATABASE_URL=${{Postgres.DATABASE_URL}}
   ENCRYPTION_KEY=<64 位十六进制，生成：openssl rand -hex 32>
   ADMIN_EMAIL=<首次平台管理员邮箱>
   ADMIN_PASSWORD=<至少 12 位的首次密码>
   ADMIN_NAME=平台管理员
   APP_URL=https://你的域名
   SYNC_INTERVAL_SECONDS=300
   ```

   `ENCRYPTION_KEY` 必须长期保留；更换它会使已保存的平台密码和上游令牌无法解密。生产环境没有默认账号、默认密码或公开注册。
4. 在 Settings → Networking → Generate Domain 生成域名，把生成的 HTTPS 地址填入 `APP_URL` 后重新部署。仅使用 Railway 默认域名时，也可不填 `APP_URL`，系统自动使用 `RAILWAY_PUBLIC_DOMAIN` 的 HTTPS 地址；自定义域名应明确填写 `APP_URL`。首次自动构建如因变量未设置而失败，补齐变量后 Redeploy 即可。
5. Healthcheck 使用 `/health`；首次启动会自动执行数据库迁移并创建唯一的平台管理员。后续部署不会覆盖用户、平台连接、账单或流水。
6. 首次登录后在「平台管理」录入上游主账号，在「代理团队」创建下级并设置价格；同步已有账号后分配归属。在「出口代理」添加实际代理，再到账号的「代理」入口绑定；旧账号还需按下文核对已有平台代理。

PostgreSQL 服务若被重命名，`DATABASE_URL` 引用中的 `Postgres` 也要改为实际服务名。应用服务无需挂载本地磁盘；数据库持久化由 PostgreSQL 服务管理。初期保持一个应用副本，使用 Dockerfile 的默认启动命令，Railway 自动注入 PORT。

生产环境不要设置 `ALLOW_LOCAL_DB=true`，也不要把 `.env`、平台密码或 refresh token 提交到 GitHub。Railway PostgreSQL 建议开启自动备份，并在正式运营前做一次恢复演练。

已有 Railway 部署：在应用服务的 Settings → Source 选择本仓库的 `main` 分支，拉取最新提交重新部署；启用自动部署时，push 后会触发构建。保留原 `DATABASE_URL` 和 `ENCRYPTION_KEY`。首次启动自动执行第 5 版代理迁移；旧账号显示未绑定或待核对，已有账单、报价和流水保留。部署完成后依次检查 `/health`、登录和「出口代理」。

## 使用顺序

1. 平台管理员在「平台管理」选择平台、填写自己的主账号和该连接的上游结算折扣；系统先登录核验，再同步平台账号。Mini CC Gateway 的固定地址为 `http://207.57.170.28:8096`，凭据在 CCMAX 数据库中加密保存，服务器到此上游的连接使用 HTTP；如上游提供 HTTPS，应更新适配器地址。
2. 在「账号管理」新建 Claude 账号，先选择自己添加的未占用代理，也可直接「添加并绑定代理」，然后选择平台上号。多平台 OAuth 可一次生成多个授权链接，但每个平台必须分别完成自己的回调授权；AI008 和 Mini CC Gateway 也可以导入 refresh token。Mini CC 的 OAuth 需粘贴完整回调地址或 `code#state`，服务器核验 state 后再提交。
3. 管理员把同步出的未归属账号分配给团队成员。归属确认后不能自行更换，避免账单漂移。
4. 在「代理团队」创建直属下级并为每个平台设置 0–1 折扣。初始价格可填写真实合同起始日以支持历史导入；后续新价格从次日北京时间生效，平台给 CCMAX 的上游折扣也按生效日留档，历史日账单不会套用后来改过的价格。
   **已有代理接入新平台时，每一层直属上级都需先为下级设置该平台价格**。首次报价可从真实合同起始日生效；新平台不会复制 AI008 的折扣，也不会默认为零。归属账号的代理链缺少当日价格会阻止本次用量入账和同步提交，请补齐价格后再同步。
5. 「用量明细」中的实时数据只用于预估。管理员用 AI008 / Mini CC Gateway 历史接口或上游确认的 Gatelink 日账单导入，核实后封存。只有封存数据能生成结算账单。Mini CC 的历史查询按北京时间整日读取，等待完整结果后才生成待审核记录；不为缺席账号补零。
6. 按「平台 → 直属代理 → 更下级」逐级生成并确认账单。确认会把本层利润写入不可重复的流水账。提现先冻结余额，再由直属上级线下打款并登记凭证。

## 平台管理与结算价格

「平台管理」每张卡片都可点击「上号到此平台」，选择已有 Claude 账号或新建账号后，流程只向所选平台提交；账号固定代理规则同样适用。多平台同时上号仍从「账号管理」进入。

管理员看到自己的上游结算折扣；每位下级只看到直属上级给自己的当前折扣及生效日期，已有改价另列待生效折扣和北京时间日期。未定价明确显示「未定价」，不套用管理员或其他成员的价格；0 折扣按 0 显示。代理团队的定价弹窗和列表也显示当前与待生效价格，保存只提交实际变更的平台。修改下级报价不会修改管理员的上游合同价，已封账金额保持固定。

连接名称可包含上游登录邮箱，仅管理员可见；下级接口统一使用平台名称和连接编号，包括总览、账号绑定、授权任务、用量和 CSV 导出。管理员的原始对账说明不向下级返回。「打开平台」及连接配置入口仅管理员可见。

## 固定出口代理

- 账号的固定代理由服务器提供给各个平台，前端不能为某个平台单独指定其他代理。OAuth 会话、任务和最终平台绑定都记录账号代理；执行任务前再次检查启用状态和一致性。代理 URL 含认证信息时加密保存，列表只显示无认证的出口地址。
- AI008 / Mini CC 上号时自动匹配或导入同一条代理，并使用 `manual` 和该平台代理 ID；完成后读回账号详情核对。上游隐藏认证且导入结果不明确时，任务停止，管理员需先在上游核实完整地址及认证，再到「出口代理 → 核实平台映射」填写 ID 和核对说明。禁止自动改用其他代理或直连。
- 旧账号先绑定与现有出口一致的固定代理。AI008 / Mini CC 可在「账号管理 → 平台管理 → 同步固定代理」修复并读回验证；Gatelink 当前未发现可用的旧账号代理修改接口，需在上游调整后，由 CCMAX 管理员「核实已有代理」并留存说明。所有已接入平台核对一致后才能继续上号或启用。
- 同步发现 AI008 / Mini CC 实际代理 ID 与映射不同时，会标记待核对并阻止后续上号及启用。上游隐藏的密码变更、Gatelink 旧账号代理变更无法通过现有读取接口完整检测，仍需管理员核实；不会把未核实状态显示为已完成。
- 固定绑定后不提供直接换代理入口，以免同一账号在多个平台使用不同出口。若代理需要迁移或更换认证，需设计逐平台迁移与核验流程后再处理。「禁止上号」只拦截新操作，现有上游账号如需停用，请在平台管理中分别操作。

## 本地开发

需要 Node.js 22：

```bash
npm ci
cp .env.example .env
# 本地没有 PostgreSQL 时，明确设置 ALLOW_LOCAL_DB=true，并填写 ENCRYPTION_KEY、ADMIN_EMAIL、ADMIN_PASSWORD
npm run dev
```

生产构建和检查：

```bash
npm run check
npm test
npm run build
npm run test:e2e # 首次需要 npx playwright install chromium
npm run start
```

本地嵌入式 PGlite 只用于开发，不建议承载生产数据。Railway 必须使用 PostgreSQL，避免容器重启造成数据丢失。

## 结算规则

每个账号每天只有一条用量记录。平台账单为 `raw_usd`，本层应收为 `raw_usd × 本层折扣`，本层利润为 `本层应收 − 下级应付`。金额保存 8 位美元小数并使用数据库事务，重复同步只更新实时快照，不重复产生收益。平台接口超时、OAuth 一次性回调和 refresh token 导入不会自动重试，任务会进入「需要核对」状态，避免外部成功而本地重复记账。

当前上游权限边界也会显示在界面：Gatelink 的历史结算接口需要管理员权限，使用代理账号时必须导入上游确认的逐账号日账单；AI008 的历史查询结果仍需要人工核对后才会进入账本。

部署到 Railway 后会自动执行所有缺少的迁移，第 4 版增加 Mini CC Gateway，第 5 版增加固定出口代理。管理员仍需在已部署实例的「平台管理」中选择 Mini CC Gateway 并录入凭据，Git 仓库不内置真实主账号、密码或代理认证信息。

当前版本的“透传”指账号上号、平台账号同步、实时/历史用量查询、启停状态、归属和账单数据透传到 CCMAX。它还不是把 Claude API 请求反向代理到上游平台的通用 API Gateway；如果需要让下级拿 CCMAX 的 API Key 直接调用模型，需要单独增加 API 密钥、额度预扣、请求审计、流式转发和上游路由层。

详细的实现范围、安全验证及运营边界见 [上线核查](docs/VERIFICATION.md)。GitHub Actions 已配置 PostgreSQL、浏览器及 Docker 构建检查。
